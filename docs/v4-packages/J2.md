## Open items and risks

1. **The DB probe is unrun.** First failures are more likely a probe typo than a design problem.
   Unverified by execution: the `slot_state` `piece` argument (only `.tile` is read when `counts` is
   empty), the 0013 `unverified_final_object` check (needs `verification_evidence` non-null: set),
   and that the probe's object key is never PUT to a store (the commit does not stat it).
2. **Model DB side is stale.** Until the probe runs, `db_copy_commit_hours` (0.33 h) and the
   serial totals mix v4 CPU with v3 DB figures; `inputs.db_pipeline` says so. After the probe,
   re-run the model with the new probe JSON; the key fallback is in place. The probe JSONs the
   model loads are fixed paths (`reports/stage1-perf-db-probe*.json`); a new probe output has to
   replace them or the model needs a flag (not added).
3. **Offline profile excludes the client-side binary COPY** (F.md: 2.7-4.1 CPU-s per 87 x 699 chunk
   for `to_pylist` + `write_row`), so v4 `cpu_us_per_level_total` omits roughly 44-67 us/level that
   the probe's COPY stage will contain. No double count in the model today (the DB side is v3).
4. **Next CPU target is the five `documents()` decodes** of the profile payload per chunk (67.9
   us/level modelled, about as much as `map_profile` and more than `write_snapshot`'s 51.3).
5. **Noise.** One benchmark run. The sum has 6x headroom under the new `< 60` limit, so noise is
   not a test risk; per-stage comparisons with the baseline are indicative only.
6. `write_snapshot`'s "writer loop" sub-stage keeps its v3 definition (total - verify - compare) and
   so now includes the Arrow-equality scan (1.065 s); the extra informational line separates it.
7. The profile script monkeypatches private `parquet._verify_written`; if package C renames it, the
   informational line disappears (guarded by `getattr`) and nothing else changes.
